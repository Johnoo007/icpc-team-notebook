## 1. วิเคราะห์ขอบเขตเวลาและพิกัดความซับซ้อน (Time Complexity Rigor)

ในการแข่งขันระดับสากล เช่น ICPC หรือ USACO การคาดเดาหรือเขียนโค้ดโดยไม่คำนวณ Time Complexity ล่วงหน้าคือการฆ่าตัวตาย ทาง Grader จะไม่อะลุ่มอล่วยให้โค้ดที่เกินเวลาแม้แต่ 0.001 วินาที

### 1.1 กฎเหล็กเมื่อ N = 2×10⁵

- **ขีดจำกัดของ CPU:** โดยทั่วไปคอมพิวเตอร์ที่ใช้ใน Grader ของการแข่งขันจะประมวลผลคำสั่งได้ประมาณ 10⁸ ครั้งต่อวินาที (100M Operations/sec)
- **ความหายนะของ O(N²):** หากใช้ลูปซ้อนลูปแบบไร้การควบคุม จำนวนรอบจะกลายเป็น (2×10⁵)² = 4×10¹⁰ รอบ ซึ่งเกินขีดจำกัดไปถึง 400 เท่า โค้ดจะติดป้าย TLE (Time Limit Exceeded) ทันที
- **สมการทางรอด:** โจทย์ลักษณะนี้บังคับทางเลือกให้คุณเดินแค่สองทาง:
  1. **O(N) (Linear Time):** วิ่งลูปเที่ยวเดียวจบ หรือใช้เทคนิคหน้าต่างเลื่อน (Sliding Window)
  2. **O(N log N) (Log-Linear Time):** อนุญาตให้มีการเรียงลำดับ (Sorting) 1 ครั้ง หรือใช้ Binary Search ค้นหาข้อมูลในลูป N รอบ

### 1.2 การเปรียบเทียบเชิงลึกของ Data Structures เพื่อความเร็วสูงสุด

การเลือกใช้ถังเก็บข้อมูลที่ไม่สอดคล้องกับพฤติกรรมของข้อมูลจะทำให้ค่าคงที่ (Constant Factor) ของเวลาบวมจน TLE ได้

| Data Structure | Search Time | Insert Time | Space Complexity | ความเสี่ยงกวนใจในการแข่ง |
| :--- | :--- | :--- | :--- | :--- |
| `std::vector` (Direct Index) | O(1) | O(1) | O(M) | กิน Memory สูงหาก M มีค่ามหาศาล (>10⁸) |
| `std::unordered_map` (Hash) | O(1) avg / O(N) worst | O(1) avg / O(N) worst | O(N) | **สูงมาก** เจอเคสดักเพื่อทำลาย Hash (Collision) |
| `std::map` (Red-Black Tree) | O(log N) | O(log N) | O(N) | เพิ่มเวลาประมวลผลโดยไม่จำเป็นหาก Key เป็นตัวเลขเรียง |

**สัญชาตญาณนักแข่ง:** หากคุณรู้ว่า Key มีขอบเขตที่แน่นอนและไม่ใหญ่เกินไป (เช่น ผลรวม Modulo M ที่ M ≤ 10⁶) **จงโยน Map ทิ้งไปแล้วใช้ Vector หรือ Array ธรรมดา** เพื่อแลกมาด้วยความเร็วระดับ O(1) แบบแท้จริง ไม่มี Constant Factor ซ่อนเร้น

## 2. อภินิหาร Prefix Sums และเทคนิคการทลายวงกลม (Cyclic Arrays)

โจทย์ระดับกลางถึงสูงมักจะนำเงื่อนไข "วงกลม" มารวมร่างกับ "การหาค่าที่คุ้มค่าที่สุด" เพื่อหลอกลวงให้คุณคิดว่าต้องใช้ลูปเช็คค่าที่เป็นไปได้ทั้งหมด

### 2.1 โครงสร้างการคำนวณช่วงแบบ O(1)

Prefix Sums ไม่ใช่แค่ตารางบวกเลขธรรมดา แต่มันคือเครื่องมือยุบมิติเวลาอาร์เรย์สะสม:

```
Prefix[i] = Prefix[i-1] + Array[i]
```

เมื่อต้องการผลรวมของช่วงตั้งแต่ดัชนี L ถึง R (แบบ 1-based):

```
Sum(L, R) = Prefix[R] - Prefix[L-1]
```

### 2.2 เทคนิค Array Doubling (การคลี่วงกลมให้เป็นเส้นตรง)

เมื่อโจทย์กำหนดให้อาร์เรย์มีลักษณะวนซ้ำเป็นวัฏจักร (เช่น สมาชิกตัวสุดท้ายเชื่อมกับตัวแรก หรือการขยับค่าเป้าหมายทำให้เศษเหลือวนรอบขอบข่าย M) โครงสร้างข้อมูลจะเกิดการสลับคิวและสับสน

**แนวคิดแก้ปัญหาระดับเซียน:** คลี่วงกลมออกเป็นเส้นตรงยาว 2 เท่า (2N) โดยการนำอาร์เรย์เดิมที่ผ่านการ Sort มาต่อท้ายตัวเอง แล้วบวกค่ารอบวง (M) เข้าไปในครึ่งหลัง

**ตัวอย่างรูปธรรม:**

สมมติ N = 3, M = 69 มีเศษเหลือจากการ Modulo คือ `[1, 64, 49]`

1. **ทำการ Sort จากน้อยไปมาก:** `R = [1, 49, 64]`
2. **ทำ Array Doubling:** ก๊อปปี้มาอีกชุดแต่บวก 69 เข้าไปในแต่ละตัว
   - 1 + 69 = 70
   - 49 + 69 = 118
   - 64 + 69 = 133
3. **อาร์เรย์ร่างสมบูรณ์ (2N):** `R' = [1, 49, 64, 70, 118, 133]`

**ทำไมวิธีนี้ถึงเปลี่ยนโลก?**

เพราะเมื่อคุณเลือกเป้าหมาย x ใดๆ คุณสามารถเปิดหน้าต่าง (Window) ขนาด N ตัวเริ่มต้นจากค่า x นั้น และข้อมูลในหน้าต่างนั้นจะ **เรียงลำดับจากน้อยไปมากอย่างสมบูรณ์แบบโดยไม่มีการวนรอบมาคั่นกลาง** เช่น

- ถ้าเลือก x = 64 หน้าต่างขนาด 3 ตัวคือ: `[64, 70, 118]`
- ค่า 70 คือตัวแทนของเลข 1 ที่ยอมเดินข้ามขอบวงกลมมาหา 64

### 2.3 การขีดเส้นแบ่งฝั่ง (Splitting Point Detection)

ในหน้าต่างขนาด N ที่เรียงลำดับแล้ว ตัวเลขจะถูกแบ่งพฤติกรรมออกเป็น 2 ฝั่งอย่างชัดเจนตามความคุ้มค่าของการใช้ Operation:

1. **ฝั่งซ้าย:** ตัวเลขที่มีค่าน้อยกว่าหรือเท่ากับจุดวิกฤต (x + M/2) กลุ่มนี้การ **เดินถอยหลัง** ลงมาหา x จะสั้นกว่า
2. **ฝั่งขวา:** ตัวเลขที่มีค่ามากกว่าจุดวิกฤต กลุ่มนี้การ **เดินหน้า** ทะลุรอบวงกลมไปหาเป้าหมายถัดไป (x + M) จะสั้นกว่า

เราใช้ `std::upper_bound` ค้นหาตำแหน่งจุดตัดนี้ได้ในเวลา O(log N) ทำให้เราไม่ต้องสแกนหาทีละตัว

## 3. พีชคณิตเชิงลึกและการคำนวณผลรวมความเสียหายใน O(1)

เมื่อเราหาจุดตัดในอาร์เรย์ขยายร่างได้แล้ว เราต้องคำนวณผลรวมจำนวนครั้งการดำเนินการ (Operations) ของสมาชิกทั้งหมดในหน้าต่างนั้นให้เสร็จทันทีใน O(1) โดยห้ามวิ่งลูปเด็ดขาด

### 3.1 การถอดสมการกลุ่มฝั่งซ้าย (เดินถอยหลัง)

สำหรับสมาชิกแต่ละตัว v ในกลุ่มซ้าย ระยะทางคือ v - x

หากกลุ่มซ้ายมีจำนวนสมาชิกเท่ากับ Count_left ผลรวมระยะทางคือ:

```
Σ(v - x) = (Σv) - (x × Count_left)
```

แปลงเป็นโค้ดดึงค่าจากตาราง Prefix Sum:

```cpp
ll first0 = (prefix[mid-1] - prefix[start-1]) - (x * ((mid-1) - start + 1));
```

### 3.2 การถอดสมการกลุ่มฝั่งขวา (เดินหน้าทบวงกลม)

สำหรับสมาชิกแต่ละตัว v ในกลุ่มขวา ระยะทางคือ (x + M) - v

หากกลุ่มขวามีจำนวนสมาชิกเท่ากับ Count_right ผลรวมระยะทางคือ:

```
Σ((x + M) - v) = ((x + M) × Count_right) - Σv
```

จัดรูปสมการใหม่ในโค้ดเพื่อความคลีนและป้องกันปัญหาเครื่องหมายติดลบ:

```cpp
ll second0 = ((x + M) * (stop - mid + 1)) - (prefix[stop] - prefix[mid-1]);
```

ด้วยการจัดรูปพีชคณิตเช่นนี้ คำตอบรวมของเป้าหมาย x ใดๆ จะเกิดขึ้นจากการเอา `first0 + second0` ซึ่งใช้เวลาประมวลผลเพียงแค่ O(1) เท่านั้น

## 4. โหมดป้องกันภัยระดับสูง (Advanced Defensive Programming)

นี่คือหมวดที่คัดสรรมาเพื่อดัดหลังและอุดจุดอ่อนความประมาทของคุณ ความผิดพลาดในส่วนนี้ไม่ใช่เพราะคุณคิดลอจิกไม่ออก แต่เป็นเพราะคุณเขียนโค้ดไม่รัดกุมพอ

### 4.1 บทเรียนราคาแพงจากบั๊ก prefix[-1] (Memory Out-of-Bounds)

การทำ 1-Based Indexing โดยการยัดเลข 0 ไว้ที่ตำแหน่งแรกของอาร์เรย์เพื่อความสะดวกในการลบช่วง Prefix เป็นเทคนิคที่ดีมาก แต่จะกลายเป็นยาพิษทันทีหากคุณทำ Binary Search คลุมเครือ

**กรณีศึกษาความล้มเหลว:**

คุณสั่ง `nums.insert(nums.begin(), 0)` เพื่อดันข้อมูลจริงไปเริ่มที่ดัชนี 1 ต่อมาคุณค้นหาตำแหน่งเริ่มต้นของ x ด้วยคำสั่ง:

```cpp
ll start = upper_bound(nums.begin(), nums.end(), x - 1) - nums.begin();
```

- เมื่อ x = 0: ค่าที่ส่งให้ค้นหาคือ x - 1 = -1
- ฟังก์ชัน `upper_bound` ค้นหาค่าที่ **มากกว่า -1** ตัวแรกสุดในอาร์เรย์ ซึ่งก็คือเลข 0 (Dummy Element ที่คุณเพิ่งยัดเข้าไปนั่นเอง!)
- ทำให้ฟังก์ชันคืนค่าดัชนีกลับมาว่า `start = 0`
- เมื่อโค้ดรันไปถึงจังหวะเรียกใช้งานตารางสะสม: `prefix[start - 1]` มันจะแปรสภาพเป็น `prefix[-1]`

**ผลลัพธ์ในสนามแข่ง:** C++ จะไม่แจ้งเตือนข้อผิดพลาดตรงๆ แต่มันจะแอบไปดึงข้อมูลขยะจากกล่องความจำข้างเคียงมาคำนวณ ส่งผลให้ Grader ตีตรายางว่า Wrong Answer (WA) แบบที่คุณหาสาเหตุไม่เจอ หรืออาจรุนแรงถึงขั้นโปรแกรมระเบิดเป็น Runtime Error (RE)

**กฎเหล็กการแก้ไขแบบรัดกุม (Defensive Search):**

ขีดเส้นใต้ห้ามให้ Binary Search วิ่งเข้าไปยุ่งกับดัชนีที่ 0 เด็ดขาด โดยการขยับ Pointer เริ่มต้นไปที่ `nums.begin() + 1` และเปลี่ยนไปใช้ `lower_bound` เพื่อล็อกเป้าค่า x ตรงๆ อย่างชัดแจ้ง:

```cpp
// บังคับค้นหาตั้งแต่ดัชนีที่ 1 เป็นต้นไป ปลอดภัยจากดัชนีติดลบ 100%
ll start = lower_bound(nums.begin() + 1, nums.end(), x) - nums.begin();
ll mid   = upper_bound(nums.begin() + 1, nums.end(), sepVal) - nums.begin();
```

### 4.2 คาถาป้องกัน Integer Overflow

ตัวแปรประเภท `int` ทั่วไปรองรับค่าสูงสุดได้เพียงประมาณ 2×10⁹

หาก N = 2×10⁵ และค่าภายในอาร์เรย์สะสมแต่ละตัวมีค่าเฉลี่ยอยู่ที่ 10⁹ ผลรวมในตาราง Prefix Sum ช่องท้ายๆ จะพุ่งไปถึง 2×10¹⁴ ซึ่งเกินขีดจำกัดของ `int` ไปอย่างมหาศาล ข้อมูลจะเกิดอาการล้นทะลัก (Overflow) กลายเป็นเลขติดลบมั่วซั่ว

**การแก้ไข:** ประกาศใช้ `long long` ในตัวแปรคำนวณคำตอบ ตารางสะสม และตัวรับอินพุตทั้งหมดให้เป็นสัญชาตญาณ

## 5. กระบวนความคิดและจิตวิญญาณแห่งชัยชนะ (Tournament Strategy)

การเป็นอันดับหนึ่งไม่ได้วัดกันที่ว่าใครพิมพ์คีย์บอร์ดเร็วกว่า แต่อยู่ที่ว่าใครโชว์ฟอร์มได้ "เลือดเย็น" และรัดกุมกว่าภายใต้แรงกดดันของเวลาการแข่งขัน

- **หยุดเขียนโค้ดทันทีถ้ากระดาษทดยังว่างเปล่า:** การรีบพิมพ์โค้ดทั้งที่ยังแยกเคสไม่เคลียร์จะทำให้คุณได้โครงสร้างโค้ดที่รกรุงรังและเต็มไปด้วยบั๊ก จงสละเวลา 5-10 นาทีแรกในการวาดเส้นจำนวน (Number Line) เขียนความสัมพันธ์ ไล่สมการพีชคณิตให้จบในกระดาษก่อนเสมอ

- **สงสัย Sample Test Case ไว้ก่อน:** จงพร่ำบอกตัวเองว่าตัวอย่างทดสอบที่โจทย์ให้มามักจะใจดีเกินไป และไม่ครอบคลุมเงื่อนไขสุดขอบ (Edge Cases) ก่อนกดส่งโค้ด คุณต้องสร้าง Custom Test Case เองเสมอ โดยมีสูตรดักบั๊กดังนี้:
  - เคสที่ค่าตัวแปรเป็นขอบล่างสุด (x = 0 หรืออาร์เรย์มีเลข 0 ทั้งหมด)
  - เคสที่ค่าตัวแปรเป็นขอบบนสุด (a_i = 10⁹)
  - เคสที่สมาชิกทุกตัวในอาร์เรย์มีค่าซ้ำกันทั้งหมด

- **ความเงียบสงบคืออาวุธระดับท็อป:** หากส่งโค้ดแล้วติดป้าย WA หรือ RE อย่าเพิ่งรีบตะบี้ตะบันแก้โค้ดส่งเดา ให้ถอยออกมาไล่ตัวแปรทีละบรรทัด (Dry Run) ตรวจสอบขอบเขตอาร์เรย์ ดัชนีลบหนึ่ง และจุดที่เสี่ยงต่อการเกิดเลขล้น ถ้าสมองเริ่มตื้อ การเดินไปล้างหน้าหรือนั่งนิ่งๆ 1 นาทีคือกลยุทธ์ที่ฉลาดกว่าการนั่งจ้องจอคอมพิวเตอร์ด้วยความโมโห
